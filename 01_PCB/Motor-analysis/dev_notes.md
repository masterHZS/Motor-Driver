## 1. 工程架构（本次交付的原理图生成器）

原理图**不是手画的**，而是由一套"单一数据源 → 多产物"的生成器产出的。位置：`01_工程/_生成器/`。

```
design.mjs   ← 唯一数据源：96 个元件 + 51 个网络（设计意图）
layout.mjs   ← 版面：9 个功能块矩形 + 块内自动排布 + 完整性检查
kicad.mjs    ← 发射 KiCad 8 .kicad_sch（符号库 + 实例 + 水平短线 + 全局标签 + 功能块框）
build.mjs    ← 生成后【独立重新解析】做端到端校验，再导出网表/BOM
render.mjs   ← 独立解析 .kicad_sch → 渲染工程图 SVG
raster.mjs   ← SVG → PNG（用 DSH 自带的 sharp）
verify.mjs   ← 纯设计层自检（引脚全覆盖 / 无重复占用 / 无悬空网络）
```

**关键设计决策**

| 决策 | 理由 |
|---|---|
| 连接靠**全局标签**而不是长走线 | 96 个元件、289 个引脚，手工布线必然出错；标签按名合并网络，`SW=3`、`LS_STAR=14` 这类关键网络一眼可查 |
| 所有符号**旋转 0°** | 避免符号空间→图纸空间的旋转变换出错（KiCad 符号 +Y 向上、图纸 +Y 向下） |
| 引脚标签**一律水平** | 竖直引脚也向"离开本体"的方向拉横线，版面紧凑、可读，且避免 KiCad 把标签竖排 |
| 多引脚同坐标（MOSFET 的 D×5 / S×3）**合并成一根线+一个标签** | 否则会产生 15 根重叠走线和标签 |
| 生成后**重新解析自己产出的文件**做校验 | 只校验设计数据是自证；解析产出文件才能发现发射器的 bug |

## 3. 踩坑注意项（下次直接避开）

1. **不要用 `indexOf(下一个标记)` 来界定嵌套 S 表达式**，必须做括号配对扫描。KiCad 文件里最后一个块的边界尤其容易出错。
2. **不要跨字段写长正则**。KiCad 的 `(pin ... (name ...) (number ...))` 括号层数深，分段解析更稳。
3. **自检必须独立于生成**。`build.mjs` 重新解析自己写出的 `.kicad_sch`，才能真正发现发射器 bug；只校验 `design.mjs` 是自证。
4. **MOSFET 的多引脚**（D=5,6,7,8,9；S=1,2,3）在符号里必须同坐标堆叠，且生成时要断言"同坐标引脚属于同一网络"。
5. `sharp` 不在项目里，要通过 `createRequire('file:///C:/Users/limer/AppData/Roaming/npm/node_modules/@deepseek-ai/dsh/')` 借用（见 `raster.mjs`）。
6. **Node 24 的内置 `node:sqlite`** 可直接读 SQLite（读 `motor-driver.eprj2` 用的就是它），不需要装依赖。
7. 嘉立创EDA专业版的 `.eprj2` 是 **SQLite + 加密正文**，文档内容不在本地（详见 `03_审核/analysis_notes.md` §5），**不要试图写回**。
8. **带极性的元件必须逐个核对极性**，不能靠"元件类型"想当然：
   - 二极管/TVS：`1 = K(阴极)`、`2 = A(阳极)`（与你 ES1D/SS110 的数据一致）
   - 电解电容：`1 = +`
   - MOSFET：`1/2/3 = S`、`4 = G`、`5–9 = D`
   **并且符号图形的极性要跟引脚编号对齐**，否则网表对、PCB 贴反。
   → 建议每次大改后用放大图目视复核一遍所有带极性元件。

## 6. 板级硬件故障追踪（2026-09-24，V3.1 实板调试）

| # | 错误现象 | 排查过程 | 根本原因 | 最终解决方案 |
|---|---|---|---|---|
| 9 | 12 V 轨只有 **1.27 V**（`U2.SW`、`U2.FB`、`L1` 后、`U4.1` 全是 1.27 V），`U2` 不烫 | 先怀疑 SW-FB 焊桥 → 但分压会被旁路，对不上。查 FB 设计值 8.66k/1k → 正常应是 VCC 的 1/9.66；**实测 FB ≈ VCC** ⇒ 反算 `R10 ≈ 0` | **`R10` 与 `R11` 贴反了**：`R10`(应 8.66 kΩ) 实际 **10 Ω**、`R11`(应 1 kΩ) 实际 **8 kΩ**。于是 `Vout = 1.25×(1+10/8000) = 1.2513 V` —— 芯片工作完全正常，只是被分压比骗了 | 两颗粒换回：`R10 = 8.66 kΩ`(`C325705`)、`R11 = 1 kΩ`(`C2907002`)。**并复核同为 0603 的 `R52`/`R53`（0 Ω）是否也被串位** |

> 教训：**贴片串位要从"分压比反算"入手**，不要先怀疑芯片坏。`Vout = Vref×(1+Rtop/Rbot)` 这个式子能一步定位到具体是哪颗电阻。
> 教训：**LDO 的发热只由压差和电流决定，与"输入是否稳定"无关** —— 12 V 越稳，8.7 V 压差越是全部变成热。这类设计必须在画板前算 `Tj`。
> ★ **Bug #11 的四条教训（数字接口类故障的通用查法）**：
> 1. **先量"两条地之间是不是 0 V"，再谈任何信号。** 逻辑地（`AGND`）与功率地（`PGND`）之间只要有偏移，**整条逻辑链的判据（VIL/VIH）全部作废**，此时从寄存器查到死也查不出问题。
> 2. **"0 Ω 电阻量出来 0 Ω" ≠ 它连通了。** 元件两端永远读 0 Ω（哪怕两端焊点全断）。要量的是**两个焊盘之间**的电压（带电、直流档），或分别量焊盘对地。虚焊/立碑用电阻档是查不出来的。
> 3. **读数"飘"是虚地的指纹**：同一节点一会儿 0 V、一会儿 2.795 V，优先怀疑参考地，而不是怀疑被测点。
> 4. **驱动不响应时，要相对驱动芯片自己的 `COM` 去量它的输入脚**（本项目 `U1.8`），不要只看 MCU 侧的逻辑 —— FD6288T 的阈值是相对 `COM(PGND)` 判的，不是相对 MCU 的 `VSS(AGND)` 判的。

### 7.2 ★ 工具链必须放在**纯 ASCII 路径**

**现象**：链接失败，报 `cannot find .../thumb/v6-m/nofp/crt0.o`、`cannot find -lc_nano` / `-lm`。

**排查**：`arm-none-eabi-gcc.exe` 正常、`arm-none-eabi/lib/thumb/v6-m/nofp/` 里 `crt0.o`、`libc_nano.a`、`libm.a` 全都在；但错误信息里路径显示为 `02_?̼?`。

**根本原因**：**xpack GCC 在 Windows 上会从自身安装路径推导 libexec/lib 目录**。工具链原本装在
`02_固件/F005_Slave/.toolchain/`（路径含中文），GCC 把非 ASCII 字符弄坏 → 推导出的库路径失效 → 链接器找不到自己的启动文件和 C 库。

**解决**：工具链移到 **`%USERPROFILE%\.toolchain-arm\`**（纯 ASCII）。`build.ps1` 的探测顺序已改为
**PATH → `%USERPROFILE%\.toolchain-arm` → 工程内 `.toolchain`**。

> 教训：**ARM GCC 工具链不要放在中文路径下**。这类故障的表象是"缺文件"，但文件其实都在 —— 要看路径编码。

### 7.3 启动文件与中断（★ 顺序陷阱）

自定义的 `startup_hc32f005.S` **不能**用通用的 `IRQ0_Handler`… 命名。官方 `interrupts_hc32f005.c`
已经为每个外设提供了**非 weak** 的向量入口（`PORT0_IRQHandler`、`TIM1_IRQHandler`… IRQn 序号见
`port/hc32f005.h` 的 `IRQn_Type`：PORT0=0…PORT3=3, UART0=6, UART1=7, SPI=10, I2C=12, TIM0=14,
TIM1=15, TIM2=16, ADTIM4=18, ADTIM5=19, ADTIM6=20, PCA=21, WDT=22, ADC=24, VC0=26, VC1=27,
LVD=28, FLASH_RAM=30, CLKTRIM=31）。向量表必须指向这些名字。

**用户 ISR 的正确定义方式**：向量入口 `TIM1_IRQHandler()` 会转发到 `__WEAK Tim1_IRQHandler()`
（受 `INT_CALLBACK_TIM1 == INT_CALLBACK_ON` 控制，见 `interrupts_hc32f005.h:72,89`）。
所以 **1 ms tick 要写 `Tim1_IRQHandler()`**；若写成 `TIM1_IRQHandler()` 会 **multiple definition** 链接失败。

### 7.4 ADT 互补 PWM 的关键参数（六步换向）

| 项 | 取值 | 依据 |
|---|---|---|
| 载波周期 | **`PERAR = 600`** @24 MHz → 20 kHz | 应用笔记：**三角波模式下 `PERAR` 是实际周期计数值的 1/2** → `PERAR = f_pclk/(2·f_pwm)` |
| 占空比 | `GCMAR = PERAR × duty` | 同上 |
| 低边常通 | **`GCMAR = 0`、`GCMCR = 0xFFFF`** | AN §3.3：`GCMCR = 0xFFFF` 时 CHB 不输出错误波形；§3.4 给出边界电平 |
| 死区 | `Adt_CfgDT(t, TRUE, TRUE)` + `Adt_SetDTUA/DTDA` | **注意 `Adt_CfgDT` 只有 3 个参数**，死区值单独设（不是一次传 8 个） |
| 固定电平 | `AdtPeriodCnts0` / `enDisVal = AdtTIMxDisValLow` | 悬空相用刹车强制两路为低 |
| 悬空相 | `GCMAR = 0xFFFF`、`GCMCR = 0` | ⚠️ **待示波器复核** |

> 🔴 **为什么必须用互补而不是"高边 PWM + 低边 GPIO 常通"**（F072 那版的做法）：
> FD6288T 高边是**自举供电**，低边必须**每个 PWM 周期都导通**给 C5/C6/C7 充电。
> 若让低边长期常通、高边做 PWM，低边就不切换 → 自举电容亏电 → **高边栅压跌落烧管**。
> 所以每颗 ADT 的互补对 + 硬件死区是本板唯一正确用法。

> ★ **Bug #21 的教训**：
> 1. **"没有示波器"不等于"测不了"**。本芯片自带 ADC + 相电压分压网络，把 ADT 三角波谷点当基准、用 `CNTER` 定位，就能做**等效时间采样**重建 20 kHz 波形（约 200 ns 分辨率）；再加上静态直流状态扫描，足以把故障定位到"哪一相、哪一条链路"。工具已固化在 `scope/pwmprobe.c` + `tests/pwm_probe.py`。
> 2. **测自举电路时，节点不能悬空等**。C5 跨在 `VB↔VS` 上，由 D1 从 VCC 充电；一旦 VS 悬空上飘，C5 会**经 D1 倒灌回 VCC**放电，读数会变成假的"高边全死"。必须**保持低边导通把 VS 钉在 0 V 充满，再 LIN↓/HIN↑ 背靠背（µs 级）切换**。我第一版就踩了这个坑，靠"逐相 + 时间分辨"才发现。
> 3. **"三相都一样"要当成线索而不是结论**。第一次测量三相高边都像"死的"，实际是 C 相好的、被测量方法掩盖了。**逐相单独做、并且带时间分辨**，才把"A/B 坏、C 好"分出来。
> 4. **母线电压是"有没有真的在推电流"的独立判据**。限流电源下母线全程不掉压，比任何软件电流读数都可靠 —— 本次就是它先坐实了"根本没电流"。

> ★ **Bug #19 的教训（三条，都关于"怎么判断"）**：
> 1. **AF 输出模式下 `PxIN` 读不到焊盘** —— 我据此得出"六路全 0、ADT 没输出"，**完全错了**（后来万用表实测是六路全高）。**判断引脚电平必须用外部仪器，或先把引脚切回 GPIO 再读**；`PxIN` 只在 GPIO 模式被验证过。
> 2. **读数"全部相同"要当心**：六个脚全 0 % 与六个脚全高，在软件侧看到的可能都是"没有变化"。**用万用表量一次就能推翻一整轮推理。**
> 3. **外设手册的"边界值行为"必须当硬约束读**。`GCMAR = 0` / `≥PERAR` 看着像"占空比 0 % / 100 %"的自然写法，实际是**触发保护、冻结输出**。这类"看起来显然"的写法，恰恰是 AN 专门用一整节（§3.4）和两张图警告的坑。

> ★ **Bug #16 的教训**：
> 1. **HAL 的 `X_GetResult()` 类 API 往往只做"把数据寄存器读出来"，不做就绪判断**，返回值恒为 `Ok`。真正的判据是状态位（这里是 `CR0.START`）。用 `== Ok` 当"数据有效"是**假保护**。
> 2. **量程反算是第一步**：读数**恰好等于满量程（`2^n − 1`，如 4095 / 65535 / 0xFFFFFFFF）**时，先怀疑"寄存器无效值/未就绪"，不要怀疑物理量真有那么大。

#### 7.7.1 最终根因与修复（2026-09-28）

后续读取 HardFault 异常栈，得到故障 PC = `0x284`、目标地址 = `0x20001000`。根因不是 DAPLink、供电或芯片，而是 `02_固件/F005_Slave/core/startup_hc32f005.S` 的 `.data` 拷贝循环比较了错误的一侧：

```asm
; 错误：Flash 源地址 + 偏移，与 RAM 的 _edata 比较，条件永远不成立
adds r4, r0, r3
cmp  r4, r2

; 正确：RAM 目标地址 + 偏移，与 RAM 的 _edata 比较
adds r4, r1, r3
cmp  r4, r2
```

旧的写法从 `0x20000000` 一直复制到栈顶外，最终在 `0x20001000` 触发总线错误。修复后重新构建并烧入 `build_gate/gate.hex`，SWD 已读到：

| 地址 | 值 | 含义 |
|---|---|---|

## 11. F005 拆除后的 F072 外接电调方案（2026-10-08）

- 背景：F005 被 UART 固件释放 P27 后，SWD 在无 nRESET 的条件下无法恢复；用户已拆除 F005。
- 替代方案：外接 HC32F072JATA，直接驱动 V3.1 板 FD6288T 的六路输入。
- 固件：`02_固件/F072_MotorCtrl/` 新增 `-Direct` 构建模式：
  - `UART0 PA9(TX) / PA10(RX)`，9600-8N1，直接对接 HostSoftware；
  - 默认 cascade 模式保持 `UART1 PA2` 半双工 115200，不影响旧级联工程。
- 六路接线：
  - PB2 → TP12 / PWM_AH / HIN1
  - PA7 → TP13 / PWM_AL / LIN1
  - PA4 → TP14 / PWM_BH / HIN2
  - PB0 → TP15 / PWM_BL / LIN2
  - PB12 → TP16 / PWM_CH / HIN3
  - PB1 → TP17 / PWM_CL / LIN3
  - F072 GND 与 V3.1 GND 共地；不要并联 3.3V/5V。
- 风险与限制：
  - 外部 F072 不读取 V3.1 的 `AIN_VBUS` / `AIN_ISENSE`，因此没有软件欠压/过流保护；
  - 首次测试必须使用限流 4S 电源，建议 12.0～16.8 V / 5 A，低油门起步；
  - V3.1 的 P01 是 `AIN_VBUS`（220k/10k 分压），不能再用作 UART RX；
  - 之前的 `build_uart_echo_p01` 方案不可用于 V3.1。

### 11.2 2026-10-08 首转失败与安全整改（F072 开环版）

- 现象：使用 `F072_MotorCtrl` 开环固件启动 2216-730KV 内转子减速电机时出现剧烈震动/异常旋转。
- 立即处置：通过 SWD 执行 `reset halt`，F072 六路 PWM 已停止；随后要求断开 4S 功率电。
- 根因判定：
  - `F072_MotorCtrl` 是固定相序、固定频率斜坡的开环六步，不带霍尔，也没有 BEMF 过零闭环；
  - 没有接 V3.1 的相电压采样（TP7/TP8/TP9）、电流采样（TP10）和母线采样（TP11）；
  - 2216-730KV 是内转子无霍尔电机，且带行星减速箱，开环固定斜坡不能满足启动和同步要求。
- 整改决定：
  - **禁止再用 `F072_MotorCtrl` 开环版直接带电机**；
  - 继续用 072，但必须移植 `F005_Slave` 的 BEMF 无感闭环状态机（HOLD/ALIGN/OPEN_LOOP/CLOSED_LOOP）；
  - F072 必须接入 V3.1 的相电压采样、电流采样、母线采样，并共地；
  - 先做“不接电机”的六路波形 + ADC 采样验证，确认相序、极性和死区后，才允许低油门接电机；
  - 首次带电机必须限流，建议 12.0–16.8 V / 5 A，逐步升压。
- 参考参数：`06_参考资料/电机参数.md`（2216-730KV，90 W，4S，最高 14600 rpm，无霍尔，极对数待确认）。


### 11.3 2026-10-08 BEMF 固定母线参数（TP11 未接）

- 用户提供的首轮母线电压：**13.00 V**。
- V3.1 相电压分压：R17/R19/R21 = 150 kΩ，R18/R20/R22 = 10 kΩ，比例 = 10/160 = 1/16。

### 11.4 2026-10-08 F072 BEMF 固件第一版

### 11.5 2026-10-08 ADC 通道验证通过
